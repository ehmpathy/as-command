# case=3 — a failed append does not stall the chain

## cell

an **awaited** write that fails, and the logic lets it throw (inventory cell 8). the unawaited variant is case=7; the variant where the logic catches it is cell 7.

## narrative

one append rejects (disk full, a run dir removed mid-run). the author sees the raw fs error, which names the code and the path (`ENOSPC`, `ENOENT … log.json`) — loud, never swallowed. the very next log, in this command or another, still lands. had the chain wedged, every later log in the process would wait forever on a dead promise, and every command would hang with no error at all.

## bdd

```
[t0] given a scheduled write that rejects
[t1] when  the next write is scheduled behind it
[t2] then  the caller of the failed write sees the original error
[t3] and   the next write still runs and resolves its own result
```

## fail-safe

- loud: the promise handed to the caller keeps the rejection
- teaches the fix: the fs error carries its code and path, which name the cause (space, a removed dir)
- live: the chain's cursor absorbs the rejection, so no later write waits on it
- for an unattended caller: an awaited rejection the logic does not catch becomes the command's thrown error, so the job exits non-zero

## a known edge, unchanged

on a dead disk, asCommand's own `await log.error('output.error')` and the `]` append fail too, so the fs error surfaces in place of the logic's error. loud, and it names the path; the behavior predates this change and is out of scope.
