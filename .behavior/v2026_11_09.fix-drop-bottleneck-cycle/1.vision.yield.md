# 1.vision — as-command drops bottleneck

## .the outcome world

- **before**: every repo that adopts the commands practice takes `@ehmpathy/as-command` as a prod dep → pulls `bottleneck@2.19.5` → `test:lint:cycles` (dpdm) fails on `Bottleneck.js ⇄ Group.js`
  - adopters patch bottleneck or exclude it in `.dpdmrc.yaml`; the lint practice forbids the exclude
  - and the dep bought naught: `new Bottleneck({ maxConcurrency: 1 })` names an option bottleneck does not read (`maxConcurrent`), so log appends were never serialized
- **after**: `as-command` has zero rate-limit deps. one promise chain serializes every file-log write
  - adopters bump as-command, drop their patch or exclude, and dpdm passes — wherever as-command was their one import path to bottleneck
  - the other packages here that require bottleneck do not reach adopter imports: `wrapper-fns@1.1.7` requires it only in `withBottleneck.js`, which its `dist/index.js` does not export; `rhachet@1.51.0` requires it only in `performInIsolatedThreads.js`, a dev cli path
  - `log.json` holds its entries in call order, whole, sealed by the final `]`
- **aha**: the fix removes a dep and *adds* the guarantee the dep was meant to give

## .mental model

- a single-lane bridge: each write waits for the one ahead to cross. no traffic light rented from a third party
- adopter's words: "as-command no longer drags bottleneck in". our words: "file-log writes run on one promise chain"

## .evaluation

- pros: removes the cycle at its source · zero new deps · real serialization where there was none · ~10 lines
- cons: one module-level chain serializes writes across all commands in the process. acceptable: log appends are small, and the old code meant a global cap of 1
- edge: a failed append must not stall the chain → the chain's cursor absorbs the rejection; the caller still sees it (case=3)
