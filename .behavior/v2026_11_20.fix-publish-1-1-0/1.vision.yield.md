# 1.vision — @ehmpathy/as-command 1.1.0 on npm

## the solution

- **cause**: #10 (declapract upgrade) moved `.github/workflows/.publish-npm.yml` from a token secret (`npm-auth-token`) to npm oidc trusted publish (`--provenance`, `id-token: write`)
- npm holds no trusted publisher for `@ehmpathy/as-command`, so the oidc exchange returns 404 and the `verify oidc auth` step halts before build
- the failed line, run `44309703170` (tag `v1.1.0`, 2026-11-18):
  ```
  ##[error]oidc: not configured for @ehmpathy/as-command (http 404). add oidc by-hand at https://www.npmjs.com/package/%40ehmpathy%2Fas-command/access
  ```
- **the cure is a package config on npmjs.com, not a file in this repo.** the workflow at the tag is correct; it lacks the registry-side half of the trust
- ⇒ per the wish, this is the admin-only wall. the ask goes to an npm maintainer of the package

## the ask — one admin action, then one rerun

🟡 **steps 1 and 2 must land within 2 days of each other.** npm: *"a newly created trusted publisher configuration must complete its first successful publish within 2 days … if the configuration is not validated within 2 days, it expires and can no longer be used or edited"* (docs.npmjs.com/trusted-publishers). so the maintainer tells the releaser the moment the record is saved, or runs step 2 themselves.

actors: **the npm maintainer** holds npm rights on the package · **the releaser** holds rerun rights on the repo · **the requester** relayed this ask and hears the result.

1. **the npm maintainer** of `@ehmpathy/as-command` opens the package's **Settings** tab (https://www.npmjs.com/package/@ehmpathy/as-command/access, the url the failed run printed) → **Trusted publishing** → GitHub Actions, and fills the form by its labels:
   - Organization or user: `ehmpathy`
   - Repository: `as-command`
   - Workflow filename: `publish.yml` (the caller, not the reusable `.publish-npm.yml`)
   - Environment name: blank
   - Allowed actions: leave as the form sets it
2. **the releaser**, within 2 days, reruns the whole failed run: `gh run rerun 44309703170 -R ehmpathy/as-command`
   - not `--failed`: that skips the install job, and the publish job restores node_modules from a cache with no fallback install. the cache evicts ~2026-11-25, after which a `--failed` rerun passes oidc and fails at build
3. done when `npm view @ehmpathy/as-command version` reads `1.1.0`
4. the releaser sends the requester the `verify oidc auth` line of the rerun (or the first red step's line), so the requester can close or route the ask

if the rerun goes red, the step that failed names the next move:

| the rerun ends | it means | next |
|---|---|---|
| green, `publish` succeeded | 1.1.0 landed | step 3 |
| green, `idempotify` reports a shasum match | an earlier run already landed 1.1.0 | step 3 |
| red at a `test` job, before `verify oidc auth` | a test flake; trust is untested | `gh run rerun 44309703170 -R ehmpathy/as-command --failed` — the full rerun's install job either restored the cache or rebuilt it, and a restore renews its 7-day clock, so `--failed` is safe for 7 days. mind the 2-day window |
| red at `verify oidc auth`, http 404 | a field of the record is off, or the record expired past 2 days | recheck the four fields (`case=2`); past 2 days, remove or replace the record (untested: npm says only that an expired record "can no longer be used or edited"); then rerun |
| red at `verify oidc auth`, any other http code (401, 403, 429, 5xx) or a `curl:` line | the token fetch or the registry failed, not the record | rerun once; if it repeats, stop and send the line to the requester |
| red at `verify oidc auth`, http 404, after all four fields were verified on a fresh record | an npm-side cause this ask does not cover | stop; send the line to the requester. no more reruns |
| red at `idempotify`, "this version failed to be published" | `publish` failed past trust (the step has `continue-on-error`) | stop and read the `publish` step's log |
| red at `build` | a new failure, past trust | stop and read the step's log |

the rerun needs no new tag and no commit: the tag `v1.1.0` already points at `ecb3eab`, whose `package.json` reads `1.1.0`. a second run cannot overwrite 1.1.0: npm forbids a republish, and the `idempotify` step reports green on a shasum match or red on a mismatch (`case=5`).

🟡 github allows a rerun only within 30 days of the original run, so step 2 works until **2026-12-18**. after that, re-push the same tag at the same commit to retrigger `publish.yml`: `git push origin :refs/tags/v1.1.0 && git push origin v1.1.0`. the re-push also reruns `provision.yml` (it fires on `v*` tags); on a tag it plans and skips apply (run `44309703163`: `github / apply` skipped), so it changes no infra. the tag carries the published github release `v1.1.0`; a tag delete can demote it to a draft, so confirm it after the re-push (`gh release view v1.1.0 -R ehmpathy/as-command --json isDraft`) and restore it with `gh release edit v1.1.0 -R ehmpathy/as-command --draft=false` if so. the two pushes are not atomic: if the second fails, push `v1.1.0` again before aught else.

## evaluation

- pro: no repo change; no token to rotate; provenance on every release
- con: the rerun path expires 2026-12-18; past that, the tag re-push is the path
- con: each package that adopts the #10 practice needs this one by-hand step per package
- edge: npm matches the **caller** workflow file (`publish.yml`). a registration under `.publish-npm.yml` would 404 the same way
- edge: npm requires cli ≥ 11.5.1 and node ≥ 22.14.0 for trusted publish. runner npm is 10.9.4, which the `verify oidc compat` step upgrades to npm 11; node is 22.21.0 via `.nvmrc` (log line `Resolved .nvmrc as 22.21.0`)

## open questions & assumptions

- **[open]** who registers the trust? `npm view @ehmpathy/as-command maintainers` lists one maintainer, npm user `uladkasach`. only that account (or an owner it adds) can open the trusted-publisher form. is the requester that account, or will the requester route the ask to it?
- **[open]** when? the rerun path (step 2) holds until 2026-12-18; past that, the tag re-push is the path
- **[answered]** which workflow filename? `publish.yml`, the caller — docs.npmjs.com/trusted-publishers: *"validation checks the calling workflow's name instead of the workflow that actually contains the publish command"*
- **[answered]** environment field? blank. `.publish-npm.yml`'s publish job declares no `environment:`, so a named one would mismatch
- **[answered]** does the practice publish once trust exists? yes. `ehmpathy/helpful-errors` v1.7.6 (run `40267747935`, 2026-10-26) runs the same `.publish-npm.yml`, prints `oidc: configured for helpful-errors`, and signs provenance
- **[answered]** is the 404 an absent `id-token` grant instead? no. neither log lists `IdToken` in its permissions block, yet helpful-errors' exchange succeeds; and as-command's log holds no `curl:` error, so the token request reached a server
- **[answered]** can a token revert publish without an admin? no. the last token publish was 1.0.5 on 2025-11-02. npm revoked all classic tokens on 2025-12-09, and granular write tokens expire within 90 days ([github changelog](https://github.blog/changelog/2025-12-09-npm-classic-tokens-revoked-session-based-auth-and-cli-token-management-now-available/)). any token from then is dead, so a revert needs an admin to mint a new one, and the next `declapract upgrade` would undo it
- **[answered]** does first registration hold an npm-side quirk? yes: a new record expires unless its first publish succeeds within 2 days, and an expired record cannot be edited (docs.npmjs.com/trusted-publishers). the ask carries it
- **[research]** does first registration hold any other npm-side quirk? unanswerable before the rerun. the verification stone settles it from the rerun's `verify oidc auth` line (2xx or 404), within ~3 minutes
