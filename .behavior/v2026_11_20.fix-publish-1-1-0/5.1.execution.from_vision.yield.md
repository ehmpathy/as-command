## 🟡 the merge order — no v1.1.x release pr merges before 1.1.0 is on npm

- `please-release` bumps **patch on any commit** but `chore(release):` (`.github/actions/please-release/action.yml:44,180`), so a merge of this `fix(publish)` pr, or of the open #9 (`fix(deps): drop bottleneck…`), to `main` opens a `v1.1.1` release pr
- the harm sits in that release pr's merge, not in the merge that opens it
- that release pr waits for an explicit release act (#11 was merged by `ehm-seaturtle`, not by auto-merge), so a merge alone ships no tag
- but if v1.1.1 is released first, it either 404s again (trust absent) or lands and makes `npm view … version` read `1.1.1`, which makes the wish's done-check false
- a second harm: `.publish-npm.yml` publishes with no `--tag`, so a 1.1.0 rerun that lands after v1.1.1 may point `latest` back at 1.1.0
- ⇒ order: trust registered → full rerun lands 1.1.0 → only then merge a release pr. this pr can wait unmerged; the done-check reads npm. the director is asked to hold #9's release pr too
- the guard is the pr body's 🟡 section plus the absent automerge (`--watch` never enables it). a draft pr would hold it harder, but `gh pr ready --undo` is not a pre-approved command here, so the route asks the director to hold the merge
