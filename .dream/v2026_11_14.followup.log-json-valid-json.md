# 🌙 dream: `log.json` should parse as json

- kind: followup (this repo, ehmpathy/as-command)
- owner: as-command maintainers
- caught 2026-11-14

## .the cue that fired

peer review r010 (round i003): the new snapshots pin a `log.json` that ends in `},\n]`, and no follow-up was on record.

## .the gap, precisely

- `asLogEntryLine` ends every entry with `,\n`, the last one too, so the file closes as `},\n]` — invalid json
- a reader cannot `JSON.parse(log.json)`; tests read entries by regex instead
- an entry logged after the seal (inventory cell 25) lands after `]`, a second way the file fails to parse
- `out.json` keeps main's byte format too: a string output is written bare (`saved reports/2026/summary.csv`) and an `undefined` output as the bare word `undefined`; neither parses as json. both are snapped in acceptance, on purpose

## .the shape of the fix

- write the separator before each entry but the first (`[` then entry, then `,\n` + entry ...), so `]` closes a valid array; the per-run state would need a "first entry" flag
- or switch to json lines (`log.jsonl`, one entry per line, no brackets): append-only, parse per line, and a late entry stays valid
- either is a contract change for readers of `log.json`: the snapshots move, and a minor or major bump is owed

## .why it is not done in this round

the wish asks to drop bottleneck and keep writes in order; it does not ask to change the file format. a format change ripples to every reader of `log.json` (fails CLEAN), so it is a separate decision.
