# 🌙 dream: `git.stage.add` stages a tracked file's removal

- kind: reseed (ehmpathy/rhachet-roles-ehmpathy, role=mechanic, skill `git.stage.add`)
- owner: rhachet-roles-ehmpathy maintainers
- caught 2026-11-14

## .the cue that fired

the commit stone of `v2026_11_09.fix-drop-bottleneck-cycle`: the pnpm migration removes `package-lock.json`, and `rhx git.stage.add package-lock.json` refused with `file not found`.

## .the gap, precisely

- the path guard demands the file exist on disk, and exempts only a modify/delete merge conflict (`git ls-files -u`)
- a plain tracked removal (`git status` shows ` D`) has no paved stage path: `git rm --cached` and `git add -u` are not pre-approved, and `git.commit.set --unstaged include` stages every change, which a bounded commit must not do
- so a lockfile swap, a file rename by delete, or any dead-file cleanup cannot land through paved skills

## .the shape of the fix

- in the guard, also accept a path git tracks: `git ls-files --error-unmatch -- "$abs_path"` succeeds → the removal is real, stage it
- `git add -- <path>` already records the removal for a tracked absent path, so the stage loop needs no change
- clamp: an integration case that removes a tracked file and asserts `git diff --cached --name-status` shows `D <path>`; red before, green after

## .why it is not done in this round

the skill belongs to rhachet-roles-ehmpathy, not this repo. the `package-lock.json` removal stays unstaged on this branch until the skill accepts it or a human stages it.
