# 🌙 dream: implicit-package-privacy must not backfill true on a published npm package

- kind: reseed
- owner: ehmpathy/declapract-typescript-ehmpathy
- caught 2026-11-16

## .the cue that fired

`declapract.upgrade` on `ehmpathy/as-command` (`useCase: npm-package`, public repo, published to npm) set `"private": true`.

## .the gap, precisely

`src/practices/provision-github/bad-practices/implicit-package-privacy/package.json.declapract.ts` backfills `"private": true` wherever `private` is absent ("fails closed"). for an npm package that is guaranteed harm:

- `npm publish` refuses a private package, so releases stop
- the shipped `provision/github.repo/resources.ts` maps `private !== false` to `visibility: 'private'`, so the next provision apply on main flips a public repo private

the fail-closed default protects services; for `npm-package` it breaks the two things the repo exists to do.

## .the shape of the fix

- for `useCase: npm-package`, do not guess `true`: refuse with a ConstraintError that names the fix (`set "private": false to keep the repo public, or true to make it private`)
- or infer: a name already on the npm registry, or the repo's current github visibility, implies `false`
- fixture: npm-package with no `private` key → check fails loud with the hint, not a silent `true`

## .why it is not done in this round

the practice lives in another repo. here, `"private": false` was set by hand (stone 3.1, D2); the explicit boolean satisfies the detector, so it holds across upgrades.
