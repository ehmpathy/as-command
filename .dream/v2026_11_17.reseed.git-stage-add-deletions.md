# 🌙 dream: git.stage.add must be able to stage a deletion

- kind: reseed
- owner: ehmpathy/rhachet-roles-ehmpathy (mechanic role: `git.stage.add`)
- caught 2026-11-17

## .the cue that fired

on `ehmpathy/as-command`, after `rhx rmsafe` removed a tracked file, `rhx git.stage.add <that path>` refused: `error: file not found: .route/v2026_11_16.declapract.upgrade/blocker/3.3.repair.cicd.defects.md`. `git rm --cached` is not paved (`rhx permissions.get --for 'git rm --cached …'` → "no paved path fits this part").

## .the gap, precisely

- `git.stage.add` checks each path exists on disk before `git add`, so a tracked-then-deleted path can never be staged
- no paved verb stages a removal (`git rm`, `git add -u`)
- the only other lever, `git.commit.set --unstaged include`, stages every untracked path too, which here would sweep in a log the human asked to keep out
- so a driver cannot commit a file removal without a guard-evasion path; here it restored the file with a resolved note instead

## .the shape of the fix

- in `git.stage.add`, accept a path absent on disk when `git ls-files --error-unmatch <path>` finds it tracked, and stage it as a removal (`git add -A -- <path>`)
- keep the not-found refusal for a path neither on disk nor tracked
- clamp: a test that rmsafe-deletes a tracked file, stages it, and asserts `git diff --cached --name-status` shows `D`

## .why it is not done in this round

the skill lives in another repo. the in-repo fallback (restore with a resolved note) keeps the tracked tree truthful.
