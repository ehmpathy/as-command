## defects

### D1 · lint · dpdm cycle inside prod dep `bottleneck`

- **what**: `test:lint:cycles` failed: `bottleneck@2.19.5/lib/Bottleneck.js -> lib/Group.js`
- **how**: the upgrade added `test:lint:cycles` (dpdm over `src/**` with `.dpdmrc.yaml` `exclude: []`). on `origin/main`, `test:lint` had no cycle step, while `bottleneck@2.19.5` and its import in `asCommand.ts` were already present, unchanged
- **why**: pre-existent, exposed by the upgrade. `asCommand.ts` imported `bottleneck`, a prod dep (abandoned since 2020) with an internal require cycle, which already shipped to consumers; the new check only made it visible. org policy (`rule.forbid.dpdm-exclude-change`, `.dpdmrc.yaml` header) forbids an exclude for a prod dep: fix upstream or replace it
- **fix**: replaced `bottleneck` with `with-bottleneck` (ehmpathy's successor, already added to deps by the upgrade):
  - `src/asCommand.ts`: `new Bottleneck({ maxConcurrency: 1 })` → `genBottleneck({ concurrency: 1 })`; `.schedule` call unchanged
  - `package.json`: removed `bottleneck`
  - 🟡 behavior note: `maxConcurrency` is not a bottleneck option (it reads `maxConcurrent`), so the old limiter never serialized file appends. the new one does, which matches the intent of the code. integration 9/9 confirms
- **fulcrum**: `F1-replace-bottleneck-with-with-bottleneck` (clean rework)

### D2 · config · package renamed + marked private

- **what**: `name: "as-command"`, `"private": true`
- **how**: `git diff origin/main -- package.json` shows the upgrade rewrote both lines. `origin/main` has `"name": "@ehmpathy/as-command"` and no `private` key; `provision/github.repo/resources.ts` is also new vs main
- **why**: the practice template set them. they would block `npm publish`, and `provision/github.repo/resources.ts:48` maps `private !== false` to repo `visibility: 'private'`, so the provision apply on main would flip the public repo private
- **fix**: `"name": "@ehmpathy/as-command"`, `"private": false` (explicit; the provision code fails closed on absent)
- 🟡 **watch**: if the declapract practice enforces these fields, the next `declapract.upgrade` will re-apply them. stone 3.3 should confirm whether the practice check flags this as drift

### D3 · lint · depcheck: unused devDependency `ts-node`

- **what**: `test:lint:deps` reported `Unused devDependencies: * ts-node` (masked by D1 until the cycle cleared)
- **how**: `git diff origin/main -- .depcheckrc.yml` removes `ts-node` from `ignores`. `origin/main` declared `"ts-node": "10.9.2"` beside `ts-jest`, and jest configs had no `esbuild-register` loader
- **why**: jest configs now load via `esbuild-register` (`@jest-config-loader esbuild-register`), so no file uses `ts-node`. grep over the repo (incl. `.github`, `.husky`, `src/.test`) finds it only in `package.json`
- **fix**: removed `ts-node` from `devDependencies`
