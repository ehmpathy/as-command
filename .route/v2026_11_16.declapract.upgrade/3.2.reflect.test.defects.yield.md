## D2a · practice bug: `projectName` names two concepts

- **practice**: `node/best-practice/package.json` (`check = FileCheckType.CONTAINS`)
  ```json
  "name": "@declapract{variable.projectName}",
  "repository": "@declapract{variable.organizationName}/@declapract{variable.projectName}",
  ```
- **the bug**: one variable is both the npm package name and the github repo slug. a scoped package (`@ehmpathy/as-command`) in repo `as-command` cannot satisfy both: `projectName: '@ehmpathy/as-command'` breaks the `repository`/`homepage`/`bugs` urls, and `projectName: 'as-command'` renames the published package
- **effect here**: the upgrade renamed the package; the restored scoped name will fail this `CONTAINS` check, so every future `declapract.upgrade` re-applies the rename
- **fix shape**: an optional `packageName` variable (default `projectName`) used only for `"name"`
- caught: `dreams/v2026_11_16.reseed.declapract-package-name-variable.md`

## D2b · practice bug: privacy backfill is wrong for `useCase: npm-package`

- **practice**: `provision-github/bad-practices/implicit-package-privacy/package.json.declapract.ts`
  - detects a `package.json` whose `private` is absent or non-boolean; the fix backfills `"private": true` ("fails closed")
- **the bug**: for `useCase: npm-package`, `"private": true` makes `npm publish` refuse, and `provision/github.repo/resources.ts` maps it to repo `visibility: 'private'`. so on a public, published package the fail-closed default is guaranteed to break publish and flip the repo private on the next provision apply
- **holds here**: an explicit `"private": false` satisfies the detector (`typeof private === 'boolean'`), so this repo's fix is stable across upgrades
- **fix shape**: for `npm-package`, infer from the repo (e.g. a scoped `name` published to npm, or the current github visibility), or refuse with a ConstraintError that asks the human to declare it, rather than a silent `true`
- caught: `dreams/v2026_11_16.reseed.declapract-privacy-backfill-npm-package.md`

## D3 · practice bug: `ts-node` removal never fires

- **practice**: `typescript-any/bad-practices/ts-node-beside-esbuild-register/package.json.declapract.ts`
  - removes `ts-node` once `esbuild-register` is present and `isTsNodeStillUsed` is false
- **the bug**: the third branch of `isTsNodeStillUsed` treats every root file that matches `/^jest\..*\.ts$/` and lacks `@jest-config-loader` as a config jest loads via ts-node. that regex also matches the setup files the tests practice itself writes. here, 6 of 10 root `jest.*.ts` lack the pragma, all of them setup files, not configs:
  - `jest.acceptance.env.ts`, `jest.acceptance.prepare.ts`, `jest.integration.env.ts`, `jest.integration.env.db.ts`, `jest.integration.prepare.ts`, `jest.unit.env.ts`
  - so `isTsNodeStillUsed` is always true, the bad practice is never detected (the exec log shows `typescript-any.best-practice` and `.legacy-tsconfig-lib` only), and depcheck fails on `ts-node` (#660, the very issue this practice was written for)
- **evidence it is live on upstream**: the local clone's `origin/main` line 45 still reads `.filter((name) => /^jest\..*\.ts$/.test(name))`, and `gh search code --repo ehmpathy/declapract-typescript-ehmpathy "jest-config-loader"` shows the same branch on the remote
- **why it shipped**: the practice's fixture `src/.test/assets/tool-swap-removals/repo-after-swaps/` holds jest configs but no `jest.*.env.ts`
- **fix shape**: match configs only, e.g. `/^jest(\..+)?\.config\.ts$/`; add `jest.*.env.ts` to the fixture beside pragma'd configs
- caught: `dreams/v2026_11_16.reseed.declapract-ts-node-jest-regex.md`
